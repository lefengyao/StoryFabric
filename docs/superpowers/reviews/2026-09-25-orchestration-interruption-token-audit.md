# 编排异常中断与 Token 消耗调查

## 现场记录

检查了用户提供项目中 2026-09-25 的会话 checkpoint；只读取运行元数据和工具调用信息，未修改项目正文。

| 运行 | 结果 | 累计模型调用 | 累计实际 Token | 关键现象 |
| --- | --- | ---: | ---: | --- |
| 首次 | `plan` 失败，`TOOL_LOOP_STOPPED` | 108 | 20,626,088 | `plan` 达到 100 轮工具调用；261 次 `get_chapter` 回执 |
| 断点重试 | `plan` 再次失败，`TOOL_LOOP_STOPPED` | 148 | 22,931,201 | 本次新增 40 次调用、2,305,113 Token；再次读取相同章节 |

第二次预算是从第一次 checkpoint 继承的累计数，不能把 22,931,201 Token 当作第二次独立消耗。`actualTokens` 来自供应商返回的 usage；最终账单仍以供应商为准。

首次运行后段在两组章节分页参数之间交替调用，随后多次重复读取同三章。原防循环逻辑只识别连续三轮完全相同的调用，所以交替循环一直运行到 100 轮上限。`plan` 每轮把之前的所有工具结果再次送入模型，记录中的估计输入从约 3,835 Token 增至约 263,729 Token。

断点恢复另有目标丢失问题：界面把“继续当前编排 checkpoint”作为新消息发出，执行器直接将其用作编排目标。调度器正确跳过了已有产物的已完成阶段；失败的 `plan` 没有可复用产物，只能重新执行，但收到的是继续命令而不是原始任务。旧界面文案没有说明该阶段会重新调用模型，容易被理解为在工具调用处精确续跑。

## 修改

- 工具循环识别 1–3 轮、重复 3 次的调用模式，包括 `A/B/A/B/A/B`，并规范化 JSON 参数键顺序。编排阶段首次检测到循环时阻止重复执行，并要求模型依据已有结果完成任务；纠偏后仍重复才中止。
- 单阶段工具轮数上限改为普通阶段 24、正文阶段 32，仍受全局调用预算限制。
- 阶段请求保留原始任务和最近完整的工具交互，以 64,000 Token 或模型上下文的 40% 中较小者为截断目标；工具调用与对应结果一起保留。单个最新工具交互超出目标时不会拆断消息对。
- 请求估算包括工具名和参数；普通阶段输出上限 16,384 Token，正文及润色阶段 32,768 Token，并受模型上下文和总预算限制。
- checkpoint 保存原始目标；恢复旧 checkpoint 时从原始会话用户消息回溯。重试时用原始目标读取项目事实并生成阶段提示。
- 界面把恢复动作标为“重试未完成阶段”，说明已完成阶段跳过、未完成阶段重新调用模型，已用 Token 沿用总预算。

## 验证边界

自动化用例覆盖交替工具调用、历史截断后的工具消息配对、单阶段调用上限、已完成阶段跳过，以及无产物的失败 `plan` 从旧 checkpoint 重试。未向真实供应商发起模型调用，因此不能保证具体模型不会形成新的非周期性无效读取；单阶段上限和预算会限制这种情况的最大范围。
