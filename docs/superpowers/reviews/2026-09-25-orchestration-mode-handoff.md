# 编排模式切换后的会话交接检查与修复

## 检查结论

- 一个会话保存在 `.storyfabric/sessions/<日期-标题-id>/session.json`。`messages`、`creativePreferences` 与最近最多 10 次 `orchestrationRuns` 属于同一个会话记录；切换模式不创建新会话。
- 同一次编排中，后续阶段的提示词会包含先前阶段产物；启用的只读子智能体发现也会传给阶段调度器。阶段知道自己属于编排，但过去没有专用工具按运行和产物 ID 查看其他编排成果。
- 原实现切回普通模式时，只把最终选中的编排文本放进共享对话消息；各阶段的完整产物保留在 `orchestrationRuns.artifacts`，却没有交给普通模式的模型，也没有暴露读取工具。因此普通模式无法可靠地继续使用计划、设定、brief 和审查等成果。
- 编排阶段的内部工具调用及结果也被追加到共享 `messages`。普通模式会原样回放这些由其他角色和模型产生的工具回合，包括可能的扩展思考块。这会污染普通模式上下文，并可能使供应商拒绝跨模型的历史格式。
- 显式 `mode: normal` 原先只控制运行分支；如果请求未同时携带新的创作偏好，旧会话保存的 `orchestrationEnabled: true` 仍影响 Skill 阶段、规则选择、普通模式专用提示和调用预算。
- 界面切换模式时先改本地运行模式，再异步保存会话偏好；保存完成前仍可发送，造成一次请求使用旧编排开关的竞态。若同时切换会话，旧保存结果还可能覆盖当前会话的界面偏好。

## 本次修复

1. 将显式的普通模式请求作为运行依据，清除该次运行继承的编排开关，并保存基本模式偏好。
2. 在模型请求与上下文压缩中排除编排阶段的内部工具回合；会话文件及界面历史保留这些记录，编排的最终答复仍可见。
3. 为普通智能体、编排阶段和只读子智能体提供 `list_orchestration_runs`、`read_orchestration_artifact`。读取范围限定在当前会话，并支持长产物分页。
4. 在模型提示中提供同一会话最近编排的运行和产物索引，要求需要完整内容时调用读取工具。阶段产物属于候选，不视为已写入项目；当前项目事实仍须由项目资料工具核对。
5. 模式偏好保存期间禁用发送与再次切换；异步保存完成后只更新仍然打开的原会话界面状态。

## 验证与边界

- 回归测试覆盖：编排切普通后按普通模式运行、旧阶段工具消息不再传给模型、普通智能体读取旧产物、新一轮编排成员读取旧运行、跨会话 ID 拒绝和分页。
- 旧版会话若没有持久化 `orchestrationRuns`，无法从最终聊天回复还原各阶段原文。仅保留最近最多 10 次编排运行。
- 代码路径与模拟供应商测试能说明根因和修复链路；真实 Windows 窗口及实际供应商的复现仍需用用户的会话验证。
- 修复阶段保持版本号不变；后续打包按项目发布规范另行更新版本并验证安装包。
